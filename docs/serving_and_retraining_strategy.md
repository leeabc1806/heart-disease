# 서빙 & 재학습 전략 — CardioCare

## 1. 서빙 방식: Model-as-a-Service (MaaS)

### 채택 이유 (3가지 기준)

| 기준 | MaaS 선택 근거 | On-Device 대비 |
|------|--------------|--------------|
| **지연 시간** | 심장병 선별은 ms 단위 실시간 응답이 아닌 진료 중 수초 내 응답으로 충분 → 서버 추론 적합 | 온디바이스는 ms 지연에 유리하나 본 도메인에서 불필요 |
| **개인정보(PHI) 관리** | 모델·추론 로그를 병원 통제하의 보안 서버에 집중 → 감사·접근통제·HIPAA 규정 준수 용이. 전송 구간 암호화 필수 | 기기 분산 저장은 분실·도난 위험, 감사 추적 어려움 |
| **업데이트 주기** | 재학습 모델을 단일 엔드포인트에 즉시 배포 → 전 사용자가 동일 최신 버전 공유, 기기별 배포 불필요 | 기기마다 업데이트를 각각 배포해야 하며, 버전 파편화 위험 |

### 구조 개요

현재 저장소는 inference.py의 CSV 배치 추론 CLI까지 구현돼 있다. 아래 중앙 API는 운영 배포 시
추가할 목표 구조이며, 현재 구현 완료 사항으로 간주하지 않는다.

```
병원 EMR / 임상 인터페이스
        │  (HTTPS, PHI 최소 전송)
        ▼
  중앙 추론 API (FastAPI / Flask)
    ├─ inference.py (Pipeline.predict + predict_proba)
    ├─ 입력 범위 검증 (validate_input)
    └─ 추론 로그 → logs/inference.log
        │
        ▼
   위험 점수 (0/1 + 확률) 반환
        │
   [경계 확률 0.4–0.6] → 의사 검토 라우팅
```

## 2. 재학습 전략

### 2-1. 트리거 기반 재학습 (Drift-triggered)

- **조건**: 핵심 특성(chol·oldpeak·thalach 등)의 KS p < 0.05가 **3일 이상 지속**
  또는 라벨 확보 후 balanced accuracy가 **0.78 이하**로 떨어질 때
- **절차**: 드리프트 알람 → 담당자 통지 → 신규 임상 데이터 수집 및 검증 → 재학습 → recall 게이팅 → 담당자 승인 → 배포

### 2-2. 정기 재학습 (Scheduled)

- **주기**: **분기별 1회** (3개월)
- **이유**: 트리거 임계치 이하의 점진적 드리프트(계절성, 임상 프로토콜 변화 등)에 대비
- 최신 임상 데이터를 누적해 모델 재학습 후 recall 게이팅 통과 시 배포

### 2-3. 폭주 피드백 루프(Feedback Loop) 방지

모델 예측을 그대로 라벨로 재사용하면 **FN(심장병 미탐지)이 학습 데이터에서도 음성으로 굳어져
recall이 자기강화적으로 악화**된다.

**방지 정책**:
- 재학습 라벨은 반드시 **의사의 확진/추적 결과(실제 정답)**만 사용
- 모델 출력을 라벨로 재사용하는 파이프라인을 기술적으로 차단 (라벨 소스 필드 필수화)

## 3. Human-in-the-loop 설계

| 지점 | 자동화 범위 | 사람 개입 내용 |
|------|-----------|-------------|
| **경계 확률 구간** | predict_proba ∈ [0.4, 0.6] 탐지 | 해당 환자를 의사 검토 큐로 라우팅, 의사가 최종 판단 |
| **드리프트 알람** | KS 검정 자동 수행, 임계치 초과 시 통지 | 담당자가 재학습 여부·일정 결정 (자동 재배포 금지) |
| **모델 배포 게이팅** | recall ≥ 현재 배포 모델 확인 자동화 | recall 게이팅 통과 후 **사람(MLOps 담당자)이 승인** 후 배포 |
| **라벨 검증** | 입력 범위·형식 자동 검증 | 임상 정답 라벨은 의료진이 확인·서명 후 학습 데이터에 포함 |

---

## 4. 재학습 데이터 관리 정책

- **데이터 버전관리**: 재학습마다 학습 데이터 스냅샷을 날짜 태그로 보관
- **최소 배치 크기**: 신규 데이터 ≥ 50건 확보 후 재학습 (소규모 노이즈 방지)
- **분포 검증**: 재학습 전 신규 데이터의 특성 분포를 기존 학습 분포와 KS 검정으로 비교, 비정상적 이동 시 데이터 품질 검토
- **PHI 처리**: 재학습 데이터에서 환자 식별 정보 제거(익명화) 후 학습 파이프라인 진입

## 5. 요약

```
드리프트 감지(KS 검정, 실시간)
    │ p < 0.05 지속 or accuracy < 0.78
    ▼
재학습 트리거 발동 → 담당자 통지
    │
    ▼ (분기별 정기 재학습도 동일 경로)
신규 임상 데이터 수집 & 익명화
    │
    ▼
Pipeline 재학습 (train.py, seed 고정)
    │
    ▼
MLflow Registry 등록 (recall 메타데이터 필수)
    │
    ▼
recall 게이팅 (≥ 현재 배포 모델)
    │ 통과
    ▼
담당자 승인 → 배포
    │ 실패
    ▼
폐기 & 원인 분석
```
